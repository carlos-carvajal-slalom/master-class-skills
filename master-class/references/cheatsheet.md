# Cheat sheet: a lesson that teaches (one page)

**The test of every lesson:** could the learner explain *what problem this solves*, *why the obvious fix fails*, and *when not to use it*, without having seen any code?

## Do
1. Open with a **concrete failure** from the running example (a message, a number, a wrong sentence).
2. Show the **obvious fix** and why it fails **before** naming the technology.
3. Name the technology only as the **consequence** of that failure.
4. One **analogy** from the learner's world; map it back explicitly.
5. Take apart **one misconception**, out loud: "So that sentence is wrong because…".
6. Say the **limits**: what it doesn't do, what it costs, the simpler alternative.
7. **Retrieval pause**: a question that applies the idea to a new case → `…` → the answer with its reason.
8. End with **one confident line**, then the **next problem** (the bridge).
9. Real values from the sources (IDs, amounts, rules). Scenarios may be hypothetical; facts may not.
10. Spoken style: "you", "we", "because", short sentences, asides in parentheses.

## Don't
- Start with "X is a …" (a definition).
- Explain the *how* (APIs, parameters, code walkthroughs) without the *what* and *why*.
- Read bullet points aloud; narration is paragraphs.
- Put more than one learning goal in a lesson.
- Invent numbers, benchmarks or quotes.
- Repeat the same opening or closing in consecutive lessons.

## Order of work (one lesson at a time)
1. Re-read: this sheet, `lesson-template.md`, `learner-profile.md`, the lesson's row in `course-map.md`, and one example script.
2. Copy the template, fill it in.
3. Run the linter; fix every ERROR and every WARN that isn't intended.
4. Read the Hook and the Retrieval pause aloud in your head: do they sound like a person talking?
5. Next lesson.

Full research and sources: `teaching-research.md` (optional reading).
